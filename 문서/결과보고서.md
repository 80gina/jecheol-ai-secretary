# Ⅰ. 과제 개요

## 1. 무엇을 만들었나

**내가 기록한 제철 식재료 가격 시계열을 이해하고, 그 데이터를 근거로 "지금 사도 되는지"까지 판정해 주는 AI 웹 서비스.**

```
사용자: "요즘 값이 어때?"
AI:     "최근 7일 평균은 4,807원/kg입니다. 평년보다 4.8% 높지만
         직전 주(5,127원/kg) 대비로는 6.2% 내리는 중이에요.
         지금은 대하·표고버섯·배추가 평균가가 낮으니 그쪽으로 밥상을 짜보세요."
```

## 2. 왜 만들었나 — 과제 요건이 아닌 실제 동기

평생학습센터 요리교실을 운영하면서 겪는 문제가 있다.
**한 달 전에 짠 식단표의 재료비가 수업 당일에 맞지 않는다.**

일반 ChatGPT에게 "이번 달 장바구니 값이 어때?"라고 물어도 **내 기록을 모르니 일반론만** 돌아온다.
그래서 내 데이터를 아는 비서가 필요했다.

## 3. 이 서비스의 설계 핵심 — 축이 두 개인 이유

| 축 | 무엇을 알려주나 | 이것만 보면 |
|---|---|---|
| **전주 대비** (단기) | 지금 오르는 중인가 내리는 중인가 | 이 시기치고 비싼지를 모름 |
| **평년 대비** (장기) | 예년 같은 시기보다 비싼가 | 지금 오르는 중인지를 모름 |

두 축이 있어야 이 구분이 나온다.

```
평년보다 싼데 오르는 중  →  지금 사는 게 낫다
평년보다 싼데 내리는 중  →  조금 더 기다려도 된다
```

> **축이 하나면 이 판단은 절대 나오지 않는다.** 이것이 이 과제에서 내가 한 가장 중요한 설계 결정이다.

## 4. 데이터

| 필드 | 의미 |
|---|---|
| `date` | 측정 날짜 (YYYY-MM-DD) |
| `value` | 그날 '제철 밥상 한 상' 기준 장바구니의 kg당 평균 소매가 (원) |
| `memo` | 그 시기의 대표 제철 품목 (예: 전어, 밤, 배추) |

**730개** 데이터 포인트 (2024-09-08 ~ 2026-09-07, 2년치). 과제 요구는 100개 이상.

> **왜 2년치인가** — "평년 대비"는 *작년 같은 시기*와 비교하는 값이다.
> **1년 미만이면 비교 대상 자체가 없다.** 자매 프로젝트 `jecheol-planner` 의
> `collect --years 2` 와 같은 기준으로 맞췄다.

## 5. 최종 결과물

| # | 요구 결과물 | 구현 | 상태 |
|:-:|---|---|:---:|
| 1 | 데이터 기반 AI 채팅 | `POST /api/chat` + 프론트 채팅 UI + 로딩 표시 | ✅ |
| 2 | 데이터 관리(CRUD) | `POST/GET/PUT/DELETE /api/data` + 화면 목록 갱신 | ✅ |

| 4 | 배포 및 문서화 | Render + Vercel + Swagger UI + README | ◻ URL 기입 |

## 6. 하지 않은 것과 그 이유

| 안 한 것 | 이유 |
|---|---|
| **프론트엔드 프레임워크** | 과제가 금지. HTML/CSS/Vanilla JS 로만 구현했다 |
| **차트 라이브러리** | 금지 규정은 없으나, 시각화를 **SVG로 직접** 그렸다. 라이브러리를 쓰면 "어떻게 그렸나"에 답할 수 없다 |
| **판정을 GPT에게 맡기기** | Ⅷ장 참조. 근거 없는 말을 지어내는 것을 막기 위해 서버가 결정적으로 판정한다 |
| **대체재 표에 가격 적어두기** | 데이터가 바뀌어도 표는 안 바뀌어 **거짓말을 하게 된다.** 조리 지식과 가격 사실을 분리했다 |

# Ⅳ. 시계열 데이터를 분석하고, 요약 정보를 만들어 서비스에서 활용하는 흐름을 설명할 수 있다

### 📋 한눈에 보기

| 단계 | 무엇을 하나 | 어디에 |
|:--:|---|---|
| 1 | Firestore에서 전체 시계열 조회 | `data_service.py` |
| 2 | 단기 축 — 최근 7일 vs 직전 7일 | `summary_service.build_summary()` |
| 3 | 장기 축 — 최근 7일 vs 같은 시기 평년 | 〃 |
| 4 | 판정 — 평년 대비를 5단계로 자름 | `VERDICT_BANDS` |
| 5 | 사람이 읽는 문장으로 변환 | `build_system_prompt()` |
| 6 | GPT 시스템 프롬프트에 주입 | `chat_service.py` |

### ✅ 확인됨

**확인 방법**

```
GET /api/data/summary
```

**응답 (발췌)**

```json
{
  "period": "2024-09-08 ~ 2026-09-07",
  "count": 730,
  "metrics": {
    "average": 4624.0, "max": 6150.0, "min": 3470.0, "latest": 4510.0,
    "recent_avg_7d": 4807.1, "prev_avg_7d": 5127.1, "change_rate_pct": -6.24,
    "normal_avg_7d": 4585.3, "vs_normal_pct": 4.85, "std_dev": 491.0
  },
  "trend": "하락 (최근 7일 평균 -6.2%)",
  "verdict": "평년 수준",
  "verdict_reason": "평년과 비슷합니다. 급하면 사고, 아니면 다음 장을 봐도 손해가 크지 않습니다. 전주 대비로는 -6.2%로 내리는 중입니다.",
  "normal_basis": "2024, 2025, 2026년 자료에서, 최근 7일 각각의 같은 달력 시기 ±7일에 해당하는 다른 해 기록 133건을 평균",
  "peak_date": "2026-02-24", "trough_date": "2024-10-18"
}
```

**증빙**: ◻ Swagger UI `/docs` 에서 `GET /api/data/summary` 실행 화면

### 왜 그렇게 했는가

**① 평년값을 "같은 달력 시기의 다른 해 평균"으로 정의했다.**

> 평년값 = 같은 달력 시기(월-일 기준 **±7일**)의 **'다른 해'** 값들의 평균

**같은 해의 값은 제외한다.** 자기 자신과 비교하면 항상 0%가 나오기 때문이다.
이 계산 근거는 `normal_basis` 필드로 **화면에 그대로 표시**한다 —
"평년보다 4.8% 높다"는 말이 어디서 나온 숫자인지 사용자가 확인할 수 있어야 한다.

**② 요약을 API로 분리한 이유**

요약을 챗 안에서만 계산했다면 화면에서 볼 수 없다. `/api/data/summary` 로 빼두니
**챗과 화면이 같은 숫자**를 쓴다. 둘이 다른 숫자를 말하면 신뢰가 무너진다.

**③ 7일을 창으로 잡은 이유**

일별 소매가는 요일 효과와 잔떨림이 있다. 7일 평균이면 **요일 효과가 한 바퀴 돌아 상쇄**된다.
3일이면 잔떨림이 남고, 30일이면 최근 변화가 묻힌다.

# Ⅴ. FastAPI 프로젝트를 라우터/서비스 등으로 분리해 구성한 기준을 설명할 수 있다

### 📋 한눈에 보기

| 층 | 아는 것 | 모르는 것 |
|---|---|---|
| **라우터** | 경로, 상태 코드, Pydantic 검증, 예외 → HTTP 변환 | Firestore, OpenAI |
| **서비스** | Firestore 접근, 통계 계산, GPT 호출 | HTTP, 상태 코드 |

> **판별법: 라우터가 `firebase_admin` 이나 `openai` 를 import 하면 잘못 나뉜 것이다.**

### ✅ 확인됨

```
backend/app/
├── main.py            FastAPI 초기화, CORS, 헬스체크
├── config.py          환경 변수 로딩
├── db.py              Firestore 연결 + 개발용 메모리 대체 저장소
├── models/schemas.py  Pydantic 요청/응답 스키마
├── routers/           ← HTTP 관심사만
│   ├── data.py            /api/data/*
│   ├── conversations.py   /api/conversations/*
│   ├── chat.py            /api/chat, /api/tools
│   └── recommend.py       [보너스] /api/recommend
└── services/          ← 도메인 로직만
    ├── data_service.py         Firestore CRUD + TTL 읽기 캐시
    ├── summary_service.py      ★ 두 축 + 판정 + 프롬프트 생성
    ├── chat_service.py         ★ 컨텍스트 주입 + GPT + 도구 호출 루프
    ├── catalog.py              도메인 지식 (분류·제철·민감도)
    ├── dishes.py               음식 82종 ↔ 재료
    ├── tools.py                [보너스] 도구 스키마 & 실행기 11종
    ├── scoring_service.py / forecast_service.py / statistics_service.py
    ├── recommend_service.py / alternatives.py / mentions.py
    └── conversation_service.py
```

**서비스 12개 · 라우터 4개**

### 왜 그렇게 했는가

**① 나눈 기준이 "파일 개수"가 아니라 "무엇을 아는가"이다.**

기능별로 자르면 파일은 많아지지만 어디를 고쳐야 할지는 여전히 모른다.
**아는 것으로 자르면** "GPT 호출을 바꾸려면 서비스, 상태 코드를 바꾸려면 라우터"가 자명해진다.

**② 도메인 지식을 별도 파일로 뺐다.**

`catalog.py`(분류·제철), `dishes.py`(음식↔재료 82종), `alternatives.py`(대체재 49품목)는
**계산이 아니라 사람이 적은 지식**이다. 계산 코드와 섞이면 지식을 고칠 때 계산이 깨진다.

**③ 경로 선언 순서 — 실제로 겪은 함정**

`/summary`, `/statistics`, `/export` 는 `/{data_id}` **위에** 선언되어 있다.
순서를 바꾸면 FastAPI가 `summary` 를 `data_id` 로 인식해 404가 난다.
**스모크 테스트에 이 셋의 순서 검사를 넣었다.**

### 📋 요약 표

| 구분 | 내용 |
|---|---|
| **분리 기준** | 라우터=HTTP만, 서비스=도메인만 |
| **자가 진단** | 라우터에 `firebase_admin`/`openai` import 가 있으면 실패 |
| **추가 분리** | 도메인 '지식' 파일을 계산 코드와 분리 |
| **자동 검사** | 경로 선언 순서를 스모크 테스트가 검사 |

# Ⅵ. Pydantic을 활용해 요청 데이터 검증을 적용한 이유와 방식을 설명할 수 있다

### ✅ 확인됨

`app/models/schemas.py` 에 요청·응답 스키마를 선언했다.

| 검증 | 내용 |
|---|---|
| 타입 | `date: str`, `value: float`, `memo: str` |
| 필수값 | `date`, `value` |
| 범위 | `0 ≤ value ≤ 10,000,000` |
| 날짜 형식 | `YYYY-MM-DD` |

**확인 방법** — 잘못된 값을 넣어본다.

```
POST /api/data   { "date": "2026-09-01", "value": "비쌈" }
→ 422 Unprocessable Entity
```

**증빙**: ◻ Swagger 에서 422 응답 화면

### 왜 그렇게 했는가

**Firestore는 스키마가 없는 NoSQL이다.** `value: "비쌈"` 같은 값도 그대로 저장된다.

그리고 이 서비스에서 그것이 왜 치명적이냐면 —
**잘못된 값 하나가 요약 계산 전체를 깨뜨리기 때문**이다.
평균·표준편차·평년 대비가 모두 `value` 를 쓰므로, 문자열 하나가 섞이면
`/api/data/summary` 가 통째로 실패하고, 그러면 **챗도 화면도 같이 죽는다.**

그래서 **앱 경계에서** 막는다. 스키마에 선언하면 세 가지가 한 번에 해결된다.

| 얻는 것 | 설명 |
|---|---|
| 자동 검증 | FastAPI가 `422` 를 자동 반환 |
| 자동 문서 | **같은 선언에서** Swagger 문서가 생성된다 |
| 응답 보증 | `response_model` 로 응답 형태도 고정 |

> **선언 한 번으로 검증과 문서가 같은 곳에서 나온다** — 이것이 Pydantic을 쓰는 실질적 이유다.
> 검증 코드와 문서를 따로 쓰면 반드시 어긋난다.

### 📋 요약 표

| 구분 | 내용 |
|---|---|
| **왜 필요한가** | Firestore는 스키마가 없어 잘못된 값이 그대로 들어간다 |
| **왜 치명적인가** | `value` 하나가 깨지면 요약 → 챗 → 화면이 연쇄로 실패 |
| **어떻게** | 타입·필수·범위·형식을 스키마에 선언 → 자동 422 |
| **덤** | Swagger 문서가 같은 선언에서 생성됨 |

# Ⅶ. Firestore에 데이터를 저장하고 CRUD로 다루는 방법을 설명할 수 있다

### ✅ 확인됨

**컬렉션 구조**

| 컬렉션 | 저장 내용 |
|---|---|
| `data` | 분석 데이터 (date, value, memo) |
| `conversations` | 대화 기록 (제목, messages, 생성 시각) |

**CRUD 엔드포인트**

| Method | Path | 설명 |
|---|---|---|
| `POST` | `/api/data` | 추가 → **201** |
| `GET` | `/api/data` | 목록 (`limit`, `start`, `end` 필터) |
| `GET` | `/api/data/{id}` | 단건 |
| `PUT` | `/api/data/{id}` | 수정 |
| `DELETE` | `/api/data/{id}` | 삭제 |
| `POST` | `/api/data/bulk` | 시드 일괄 업로드 |

**연결 방식**

- 서비스 계정 키는 **코드에 하드코딩하지 않고** 환경 변수로 관리 (`config.py`)
- Firestore 접근은 `db.py` 한 곳으로 모았다

**증빙**: ◻ Firebase 콘솔의 `data` / `conversations` 컬렉션 화면

### 왜 그렇게 했는가

**① 개발용 메모리 대체 저장소를 만들었다.**

`db.py` 는 Firebase 키가 없으면 **메모리 저장소로 자동 전환**한다.

> 키 발급을 기다리는 동안 개발이 멈추지 않게 하려고 넣었다.
> 결과적으로 `smoke_test.py` 가 **Firebase 없이 120개 항목을 검증**할 수 있게 되었다.

**② TTL 읽기 캐시를 넣었다.**

`/api/data/summary` 는 매번 **전체 시계열**을 읽는다. 챗 한 번에 한 번씩 전체 조회를 하면
Firestore 읽기 횟수가 빠르게 늘어난다. 짧은 TTL 캐시로 반복 조회를 줄였다.

**③ 컬렉션을 둘로 나눈 이유**

분석 데이터와 대화 기록은 **수명과 접근 패턴이 다르다.** 데이터는 자주 읽고 드물게 쓰며,
대화는 계속 쌓인다. 한 컬렉션에 섞으면 목록 조회가 무거워진다.

### 📋 요약 표

| 구분 | 내용 |
|---|---|
| **컬렉션** | `data` (분석), `conversations` (대화) — 접근 패턴이 달라 분리 |
| **CRUD** | POST/GET/PUT/DELETE + bulk |
| **키 관리** | 환경 변수. 코드·저장소에 없음 |
| **개발 편의** | 키 없을 때 메모리 저장소로 자동 전환 |
| **비용 관리** | 전체 조회에 TTL 캐시 |

# Ⅷ. "데이터 요약을 시스템 프롬프트에 주입하는 방식(컨텍스트 주입)"의 원리를 설명할 수 있다

> **이 장이 이 과제의 핵심이다.**

### 📋 한눈에 보기

**GPT는 상태가 없다.** 이전에 내 데이터를 보여줬어도 다음 요청에서는 기억하지 못한다.
그래서 **매 요청마다 요약을 `system` 메시지로 다시 넣는다.**

### ✅ 확인됨 — 동작 흐름

```
[POST /api/chat]
      │
      ├─ 1. build_summary()          Firestore 전체 조회
      │      ├ 단기 축: 최근 7일 vs 직전 7일        → 전주 대비 %
      │      ├ 장기 축: 최근 7일 vs 같은 시기 평년   → 평년 대비 %
      │      └ 판정  : 평년 대비를 5단계로 자름     → verdict + 이유 문장
      │
      ├─ 2. build_system_prompt()    요약과 판정을 사람이 읽는 문장으로 변환
      │        ↓
      │      "[서버가 내린 판정]  ※ 아래 판정과 이유를 그대로 근거로 쓰세요
      │       - 판정: 평년 수준
      │       - 이유: 평년과 비슷합니다. … 전주 대비로는 -6.2%로 내리는 중입니다."
      │
      ├─ 3. GPT 호출   [system: 요약+판정] + [최근 8턴] + [user: 질문]
      │        └ 필요하면 도구 호출 (최대 3라운드)
      │
      └─ 4. conversations 컬렉션에 자동 저장
```

**증빙**: ◻ 채팅 화면 (질문 + 답변에 실제 수치가 포함된 것이 보이게)

### 왜 그렇게 했는가 — 이 과제에서 가장 중요한 판단

**① 판정을 GPT가 아니라 서버가 내린다.**

GPT에게 "평균 4,624원"이라는 **날숫자만** 주면
**"비싼 편이네요" 같은 근거 없는 말을 지어낸다.**

그래서 판정은 **결정적(deterministic)으로 서버가** 내리고,
GPT는 **그 문장에 말투만 입히게** 한다. 틀릴 구멍이 막힌다.

| 평년 대비 | 판정 |
|---|---|
| ≤ −12% | 지금 사세요 |
| ≤ −4% | 사도 좋습니다 |
| < +5% | 평년 수준 |
| < +12% | 조금 비쌉니다 |
| ≥ +12% | 미루는 편이 낫습니다 |

판정 밴드는 `summary_service.VERDICT_BANDS` **한 곳에만** 정의되어 있고,
프롬프트·프론트·문서가 모두 이 값을 쓴다. 세 군데에 따로 적으면 반드시 어긋난다.

**② 최근 8턴만 넣는 이유**

대화가 길어지면 토큰이 계속 늘어난다. 최근 8턴으로 자르되,
**요약은 매번 새로 계산해 넣는다.** 오래된 대화는 잊어도 되지만
**데이터는 항상 최신이어야** 하기 때문이다.

**③ 계산인 것을 예언처럼 말하지 않게 하기**

예측 관련 답변은 GPT가 가장 단정하기 쉬운 지점이다. 시스템 프롬프트에 규칙을 못박았다.

> "~할 것입니다" 대신 **"지금까지의 패턴대로라면 ~쯤으로 계산됩니다"** 처럼 말하고,
> caveat(작황 급변·명절 수요는 반영 안 됨)를 반드시 함께 전하세요.

`get_item_scores` 응답에는 각 축에 `source: measured | reference` 를 실어 보내
**"참고값을 데이터인 것처럼 말하지 말라"** 고 지시한다.

### 📋 요약 표

| 구분 | 내용 |
|---|---|
| **왜 주입하나** | GPT는 상태가 없다. 매 요청마다 다시 넣어야 한다 |
| **무엇을 주입하나** | 두 축 요약 + **서버가 내린 판정** + 판정 이유 문장 |
| **핵심 판단** | 판정은 서버가, 말투만 GPT가 — 지어내기를 구조적으로 차단 |
| **단일 출처** | `VERDICT_BANDS` 한 곳 → 프롬프트·화면·문서가 공유 |
| **환각 방지** | 예측은 "계산됩니다" 어투 강제, 참고값은 `source` 표기 |

# Ⅸ. 배포 환경에서 CORS/환경변수/키 관리가 왜 필요한지 설명할 수 있다

### ✅ 확인됨

| 환경 변수 | 어디 | 용도 |
|---|---|---|
| `OPENAI_API_KEY` | Render | GPT 호출 |
| `FIREBASE_SERVICE_ACCOUNT_JSON` | Render | Firestore 인증 |
| `ALLOWED_ORIGINS` | Render | CORS 허용 도메인 |
| `API_BASE_URL` | Vercel | 프론트가 부를 백엔드 주소 |

**증빙**: ◻ Render 환경변수 화면 · ◻ Vercel 환경변수 화면

### 왜 그렇게 했는가

**① CORS가 왜 필요한가**

프론트(`*.vercel.app`)와 백엔드(`*.onrender.com`)는 **출처가 다르다.**
브라우저의 **동일 출처 정책**이 기본적으로 요청을 차단하므로,
서버가 "이 출처는 허용한다"고 **응답 헤더로** 알려줘야 한다.

> 허용 목록을 코드에 박으면 **배포 주소가 바뀔 때마다 재배포**해야 한다.
> 그래서 환경 변수(`ALLOWED_ORIGINS`)로 뒀다.

**② 키를 환경 변수로 두는 이유 — 두 가지다**

| 이유 | 설명 |
|---|---|
| **보안** | 저장소가 공개되면 키가 그대로 노출된다. OpenAI 키는 **과금**과 직결된다 |
| **환경 분리** | 로컬·배포가 다른 키를 쓸 수 있다. 코드를 안 고치고 환경만 바꾸면 된다 |

`.env` 는 `.gitignore` 로 제외하고, `.env.example` 에 **키 이름만** 올려
"무엇을 채워야 하는지"는 알 수 있게 했다.

**③ 콜드스타트 대응**

Render 무료 티어는 15분간 요청이 없으면 절전한다. 첫 응답까지 **최대 60초**가 걸린다.

> 사용자는 이것을 "고장"으로 인식한다. 그래서 프론트가 페이지 로드 직후 `/health` 를 호출해
> **서버를 미리 깨우고**, 2.5초 이상 걸리면 상단에 안내 배너를 띄운다.
> 과제 요구인 "슬립·콜드스타트 고려 안내"에 해당한다.

**④ 비용 관리**

개발·테스트 단계에서 요청 횟수와 `max_tokens` 를 제한하고,
**작은 테스트 데이터로 먼저 검증**했다. `smoke_test.py` 는 OpenAI 호출 없이 도는 검사다.

### 📋 요약 표

| 구분 | 내용 |
|---|---|
| **CORS** | 출처가 다르므로 서버가 헤더로 허용을 알려야 한다. 목록은 환경 변수 |
| **환경 변수** | 보안(과금 키 노출 방지) + 환경 분리 |
| **저장소 정책** | `.env` 제외, `.env.example` 로 이름만 공개 |
| **콜드스타트** | `/health` 선호출로 미리 깨우기 + 안내 배너 |
| **비용** | 토큰 제한 + OpenAI 없이 도는 스모크 테스트 |

### 환경 변수로 뺀 것을 실제로 갈아끼워 봤다 — 공급자 교체

과제 요건은 "키를 환경 변수로 관리하라"까지입니다. 그러나 **환경 변수로 뺀 설계가 실제로
값을 하는지는 갈아끼워 봐야 압니다.** 개발 중 OpenAI 크레딧이 소진되어 이 검증을 실제로 하게
됐습니다.

처음 코드는 OpenAI만 볼 줄 알았습니다. 접속 주소가 라이브러리 기본값에 묶여 있었기 때문입니다.
주소를 밖으로 빼서 세 값(주소·모델·키)만으로 공급자가 정해지도록 고쳤습니다.

| 공급자 | `OPENAI_BASE_URL` | `OPENAI_MODEL` |
|---|---|---|
| OpenAI | (비움) | `gpt-4o-mini` |
| Google Gemini | `https://generativelanguage.googleapis.com/v1beta/openai/` | `gemini-3.6-flash` |
| 코디세이 게이트웨이 | `https://copa.codyssey.kr/v1` | `gpt-5-mini` |

**코드는 한 줄도 바꾸지 않고** 세 공급자를 오갔습니다. 최종 배포는 코디세이 게이트웨이를 씁니다.

다만 "OpenAI 호환"이라고 해서 받아주는 항목까지 같지는 않았습니다. `gpt-5` 계열은 `max_tokens`
대신 `max_completion_tokens` 를 쓰고 `temperature` 는 기본값만 받습니다. 모델 이름을 코드에
나열하면 새 모델이 나올 때마다 코드를 고쳐야 하므로, **서버가 거부한 사유를 읽고 요청을 스스로
맞추도록** 했습니다. 사유를 알려주지 않는 게이트웨이를 대비해 보수적인 형태로 한 단계씩 줄이며
재시도하는 길도 함께 뒀습니다.

> **얻은 것** — "환경 변수로 뺐다"는 말과 "실제로 갈아끼워진다"는 사실은 다릅니다.
> 갈아끼워 보기 전까지는 전자만 있었습니다.

# Ⅹ. 보너스 ① — Function Calling + MCP 멀티채널 연동

## 1. 왜 필요한가

컨텍스트 주입은 **요약에 담긴 것만** 답할 수 있다.
"6월 중 제일 쌌던 날"처럼 **개별 레코드**를 봐야 하는 질문은 GPT가 직접 조회해야 한다.

## 2. 도구 11종

| 도구 | 호출 근거 | 예시 질문 |
|---|---|---|
| `get_data_summary` | 요약만으로 충분 | "전반적으로 어때?" |
| `query_data` | 특정 기간 **개별 레코드** 필요 | "지난주 기록 보여줘" |
| `find_extreme` | 기간 내 **극값 탐색** | "제일 쌌던 날은?" |
| `get_item_verdict` | **한 품목**의 두 축 판정 | "배추 지금 사도 돼?" |
| `browse_by_category` | **갈래**로 훑기 | "수산물 중에 살 만한 거?" |
| `get_item_scores` | **전반적 평가** | "지금 시금치 어때?" |
| `get_swot_analysis` | **장보기 계획** 판단 | "이번 주 뭘 미루고 뭘 사?" |
| `get_price_forecast` | **앞으로**를 물음 | "김장철 배추값 어떻게 될까?" |
| `recommend_dishes` | **뭘 만들지**부터 | "도시락 반찬 추천해줘" |
| `suggest_alternative` | 판정이 나빠 **대안** 필요 | "배추 비싼데 뭘 대신 쓰지?" |
| `list_past_conversations` | **대화 기록** 조회 | "전에 무슨 얘기 했지?" |

> **왜 판단형 도구를 섞었나** — 전부 조회 도구였다면 GPT는 그냥 첫 번째 것만 부른다.
> `suggest_alternative`, `get_swot_analysis`, `recommend_dishes` 처럼 **판단이 필요한 도구**가
> 섞여 있어야 GPT가 도구를 **"고르는"** 행동이 실제로 나타난다.

## 3. 호출 흐름 (실제 사례)

```
사용자: "6월 중에 제일 쌌던 날이 언제야?"
   ▼
[POST /api/chat]  system(요약+판정) + tools 스키마 11개
   ▼
GPT 1차: finish_reason = "tool_calls"
   └ 판단 근거: 요약에는 '전체 최저가'만 있고 '6월 한정'은 없다
   └ 호출: find_extreme({ mode:"min", start:"2026-06-01", end:"2026-06-30" })
   ▼
서버 실행 → { found:true, date:"2026-06-10", value:4090, memo:"매실" }
   ▼
GPT 2차: "6월에는 10일이 4,090원/kg으로 가장 저렴했어요. 매실 제철이었네요."
   ▼
화면 하단에 호출 추적 표시: 🔧 find_extreme({"mode":"min",...})
```

무한 호출을 막기 위해 도구 라운드는 **최대 3회** (`MAX_TOOL_ROUNDS`).

## 4. 안전장치

| 장치 | 이유 |
|---|---|
| `TOOL_SPECS` ↔ `TOOL_IMPLS` **키 일치 검사** | 스키마만 늘리고 구현을 빠뜨리면 **GPT가 부른 뒤에야** 실패한다. 그때는 이미 토큰을 쓴 뒤다 |
| 대체재 표에 **가격을 안 적음** | 데이터가 바뀌어도 표는 안 바뀌어 거짓말을 하게 된다. 스모크 테스트가 "표에 숫자+원 형태가 없는지" 검사 |
| 호출 추적 화면 표시 | 어떤 도구를 왜 불렀는지 사용자가 볼 수 있어야 신뢰가 생긴다 |

## 5. MCP Server — 외부 채널 검증

동일한 11개 도구를 **MCP 프로토콜로도** 노출해, Claude Desktop 같은 외부 클라이언트에서도
조회할 수 있음을 확인했다.

```bash
cd backend
pip install "mcp[cli]"
python mcp_server/server.py
```

> **같은 도구를 두 채널(웹 챗 / MCP)에서 쓴다**는 것이 이 보너스의 요점이다.
> 도구를 서비스 계층에 두었기 때문에 채널만 바꿔 끼울 수 있었다 — Ⅴ장의 분리가 여기서 값을 한다.

**증빙**: ◻ Claude Desktop 에서 도구 호출된 화면

### 시각화를 SVG로 직접 그린 이유

차트 라이브러리를 쓰면 그래프는 빨리 나온다. 그러나 **"어떻게 그렸나"에 답할 수 없다.**

프레임워크 금지 규정의 취지와도 맞다고 판단했다.

### 서버 추천 / AI 추천을 사용자가 고르게 한 이유

같은 질문에 **규칙 기반 서버 추천**과 **GPT 추천**은 다른 답을 낸다.
어느 하나를 감추면 사용자는 그것이 유일한 답이라고 믿는다.
**둘을 나란히 보여주고 고르게** 하면, 추천이 절대적 답이 아니라는 것이 드러난다.

**증빙**: ◻ 시각화 화면 · ◻ 다크 모드 화면 · ◻ 내보내기 동작

# XII. 오류 및 수정 이력

> 겪고 해결한 과정 자체가 학습 성과다.

| # | 증상 | 원인 | 해결 | 배운 점 |
|:-:|---|---|---|---|
| 1 | `/api/data/summary` 가 404 | `/{data_id}` 가 위에 선언되어 `summary` 를 id 로 인식 | 구체 경로를 변수 경로 **위로** 이동 | FastAPI 경로는 **선언 순서**가 곧 우선순위다. 스모크 테스트에 순서 검사 추가 |
| 2 | GPT가 근거 없이 "비싼 편이네요" | 날숫자만 주고 판정을 맡김 | 판정을 **서버가** 내리고 문장까지 만들어 주입 | LLM에게 **판단을 맡기지 말고 표현만 맡긴다** |
| 3 | 평년 대비가 항상 0% | 평년 계산에 **같은 해** 값이 포함됨 | 같은 해 제외, 다른 해만 평균 | 자기 자신과 비교하면 차이가 안 나온다 |
| 4 | 첫 접속이 매우 느림 | Render 무료 티어 콜드스타트 | `/health` 선호출 + 안내 배너 | 느린 것과 고장난 것을 **사용자는 구분 못 한다.** 알려줘야 한다 |
| 5 | Render Blueprint 인식 실패 | `render.yaml` 이 `backend/` 안에 있었음 | `git mv` 로 저장소 루트로 이동, `rootDir: backend` 로 지정 | 설정 파일의 **위치 자체가 규약**인 경우가 있다 |
| 6 | 전 API가 500 | Firebase 일일 읽기 한도 초과 (`ResourceExhausted`) | 서버 로그 마지막 줄에서 확인 → `USE_MEMORY_DB` 로 전환 | 화면이 추측한 원인 3개는 **모두 틀렸다.** 로그가 답이었다 |
| 7 | `403 permission_denied` | Anthropic 호환 키를 OpenAI 호환 통로에 사용 | 게이트웨이에서 OpenAI 호환 키를 새로 발급 | 같은 서비스도 **규격별로 키가 다르다** |
| 8 | `200` 인데 본문이 HTML | 접속 주소가 학습 사이트(`usr.`)였고, 그 사이트는 어떤 경로든 홈페이지를 돌려줌 | API 호스트(`copa.`)로 교정 | **상태 코드만 보면 속는다.** `Content-Type` 을 함께 봐야 한다 |
| 9 | `400 thought_signature is missing` | 도구 호출 응답에서 필요한 필드만 골라 담아 서명이 유실됨 | 모델 응답을 **원형 그대로** 되돌려주도록 변경 | 공급자가 덧붙인 것을 **함부로 버리지 않는다** |
| 10 | 파라미터 오류가 `429 Quota exceeded` 로 보임 | 게이트웨이가 상위 오류를 자기 코드로 바꿔 전달 | 같은 키로 **직접 호출**해 200을 확인 → 우리 요청과 한 항목씩 대조 | 오류 코드의 **말**이 아니라 **차이**를 본다. 잔여 토큰 300만 중 6천만 쓴 상태였다 |

# XIII. 자기 평가 및 향후 개선

## 1. 잘한 점

| # | 내용 |
|:-:|---|
| 1 | **판정을 서버가 내리게 한 것.** LLM의 환각을 구조로 막았다 |
| 2 | **축을 두 개로 잡은 것.** 하나였으면 "싼데 오르는 중"을 구분할 수 없었다 |
| 3 | **키 없이도 도는 개발 환경.** 발급 대기 중에도 진행이 멈추지 않았다 |
| 4 | **스모크 테스트 120항목.** 경로 순서, 도구 키 일치처럼 눈에 안 보이는 실수를 잡았다 |
| 5 | **도구를 서비스 계층에 둔 것.** 그래서 MCP 채널을 얹을 때 코드를 거의 안 고쳤다 |

## 2. 아쉬운 점

| # | 내용 |
|:-:|---|
| 1 | 판정 밴드(±4%, ±12%)는 **내가 정한 값**이다. 근거를 데이터로 검증하지 못했다 |
| 2 | 대화 기록이 쌓일수록 목록 조회가 무거워질 구조다. 페이지네이션이 없다 |
| 3 | 도구 호출 실패 시 사용자에게 보이는 안내가 아직 거칠다 |
| 4 | 프론트 테스트가 없다. 백엔드만 스모크 테스트가 있다 |

## 3. 개선 방향

| 우선순위 | 개선안 | 기대 효과 |
|:---:|---|---|
| 1 | 판정 밴드를 **표준편차 기반**으로 재정의 | 임의값이 아니라 데이터에서 나온 기준이 된다 |
| 2 | 대화 목록 페이지네이션 | 기록이 쌓여도 화면이 느려지지 않는다 |
| 3 | `jecheol-planner` 실측 데이터로 전면 교체 | 생성 데이터가 아닌 **실제 시세**로 판정 |
| 4 | 도구 호출 실패 시나리오 안내 문구 정리 | 오류 상황에서도 서비스가 답을 준다 |

## 4. 배운 것

**LLM에게 무엇을 시키고 무엇을 시키지 말아야 하는지**를 배웠다.

처음에는 "GPT가 알아서 판단하겠지" 하고 숫자만 넘겼다. 그랬더니 **그럴듯하지만 근거 없는 말**이 나왔다.
계산과 판정은 코드가 하고, GPT는 **그 결과를 사람 말로 옮기는 일**만 맡기니 답이 안정됐다.

그리고 **분리해 두면 나중에 값을 한다**는 것도 배웠다.
도구를 서비스 계층에 뒀더니 MCP 채널을 얹을 때 새로 짤 것이 거의 없었다.
